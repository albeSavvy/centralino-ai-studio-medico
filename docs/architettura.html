1 Ingresso — due canali

Amazon Connect
Telefonia inbound · numero reale
Perché: contact center gestito, serverless e pay-per-use — evita un centralino telefonico fisico o VoIP da amministrare. Fornisce il numero e porta la voce nel cloud.
Amazon Lex V2
ASR / TTS italiano (Polly), barge-in
Perché: integrato nativamente con Connect e già pronto per l'italiano (voce + riconoscimento). Trasforma il parlato in testo per il motore, senza costruire un ASR/TTS da zero.
Strato voce — a pagamento, attivabile
Amazon API Gateway
Canale testo /simulate — Free Tier, per test senza telefono
Perché: espone un endpoint HTTP gestito (auth, throttling) senza gestire web server. Permette di testare tutto il dialogo via testo a costo zero, senza il telefono.

2 Cervello conversazionale — serverless

AWS Lambda · motore-conversazionale
Possiede lo stato del dialogo, tool-use, timeout/fallback
Perché: scelta di mettere la logica qui (non in Lex) per avere libertà di dialogo e controllo su timeout/fallback. Serverless: paga solo quando c'è una chiamata, zero costo a riposo.
Amazon Bedrock — Claude Haiku 4.5
Dialogo in italiano + estrazione strutturata dei dati
Perché: accesso a LLM via API senza gestire modelli/GPU; Haiku è il più economico e veloce (adatto al vincolo costo-zero). È il "cervello" che capisce il paziente e struttura i dati.
AWS Lambda · assegnatore-colloquio
Sceglie il primo slot libero
Perché: responsabilità isolata in una funzione dedicata (disaccoppiamento): la logica degli slot può evolvere senza toccare il motore. Serverless come le altre.
Amazon DynamoDB
Single-table: PATIENT / DOCTOR / APPT · sessione dialogo
Perché: NoSQL serverless on-demand — niente DB server da gestire, scala a zero. Preferito a RDS per il costo-zero a riposo e la velocità su accessi a chiave.

3 Orchestrazione conferma 8h

AWS Step Functions
confirmation-workflow · race Wait 8h ↔ callback (waitForTaskToken)
Perché: l'attesa di 8h e la gestione degli stati sarebbero fragili dentro una Lambda (max 15 min, nessuna persistenza). Step Functions gestisce in modo dichiarativo attese lunghe, scelte e retry.
AWS Lambda · notificatore-telegram
Invia recap + taskToken al gruppo dottoresse
Perché: un singolo compito (notificare) isolato in una funzione; invocata dallo workflow quando serve, zero costo a riposo.
AWS Lambda · telegram-callback
Riceve il click · conditional write (mutua esclusione)
Perché: gestisce il click sul bottone e sblocca lo workflow. La conditional write su DynamoDB garantisce "vince la prima azione" senza lock espliciti.
AWS Lambda · scrivi-calendario
Su conferma: crea evento definitivo
Perché: isola l'integrazione col calendario dietro una funzione: il sink (Google oggi, altro domani) è sostituibile senza toccare il resto.
AWS Lambda · gestore-consenso
Su conferma: email + PDF consenso
Perché: compito dedicato all'invio del consenso, separato dalla scrittura calendario: ogni passo dello workflow è una funzione a sé, testabile da sola.
Amazon SES
Invio email di consenso
Perché: servizio email gestito e a basso costo, nativo AWS — evita un server SMTP. Adatto all'invio transazionale (una mail per conferma).

Integrazioni esterne

Google Calendar API
freebusy + creazione evento colloquio
Perché: lo studio usa già Google Calendar — ci si integra invece di imporre un nuovo gestionale. Dietro un'astrazione, così domani si può sostituire con un gestionale medico.
Telegram Bot API
Recap con bottoni Conferma / Blocker
Perché: canale gratuito, immediato e coi bottoni interattivi, già usato dalle dottoresse. Evita di costruire un'app di notifica dedicata.

Sicurezza

AWS Secrets Manager
Service Account Google + token bot Telegram (mai nel codice)
Perché: le credenziali non devono mai stare nel codice o in variabili in chiaro. Letto a runtime con accesso controllato da IAM — scelta di sicurezza by design.

Flusso end-to-end (verificato dal vivo)

  • 1 → 2 · Il paziente chiama (o scrive). Connect+Lex passano il testo alla Lambda motore, che dialoga via Bedrock e salva i dati in DynamoDB.
  • 2 → 3 · Raccolti i dati, l'assegnatore sceglie lo slot e la Lambda avvia Step Functions (appuntamento in stato PROVVISORIO).
  • 3 · Step Functions notifica Telegram e attende: vince il primo tra il click (conferma/blocker) e il timeout di 8h. La conditional write su DynamoDB garantisce la mutua esclusione.
  • 3 → fine · Su conferma: evento su Google Calendar + email di consenso via SES. La state machine chiude con esito SUCCEEDED.
